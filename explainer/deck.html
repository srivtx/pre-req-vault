First principles

Solana is one shared ledger

Code and data are separate

A program is deployed code at an address. It holds no memory between calls. All lasting state lives in accounts.

You declare accounts up front

A transaction lists every account it will touch before the program runs. That is why the code always declares accounts first.

Mental model: the ledger is a global key–value store; "running a program" proposes a change to it.
First principles

A transaction = accounts + instructions + signatures

  • accounts[] — everything I will read or write
  • instructions[] — one call into one program (function + args)
  • signatures — proof the key owners authorized it

An instruction

"run deposit with amount = 1 SOL, using these accounts." A transaction can chain several — that is how one action touches multiple programs.

A signed account is marked "signer"; the runtime checks this before the program runs.
First principles

Programs are stateless; accounts hold state

A program is deployed executable code with no memory of its own. When it runs, the accounts you passed in are its only inputs and the only things it can modify.

Mental shortcut: a program is a function; an account is a mutable argument you hand it.
First principles

Inside an account

  • address — its public key
  • owner — which program may write its data
  • lamports — its SOL balance
  • data — arbitrary bytes (state lives here)
  • executable — true only for programs
  • signer / writable — per-transaction flags
Only the account's owner program may change its data or debit its lamports. That is why moving SOL out of the vault needs the vault's cooperation.
First principles

Rent: storing data costs SOL

Keeping data on the ledger costs a little SOL called rent. Creating an account pre-pays rent (recoverable by closing it).

initialize

user is the payer — funds rent for vault_state.

close

close = user returns the rent when the account is deleted.

First principles

PDAs: addresses with no private key

We want a vault holding your SOL that only our program can empty. A normal account is owned by a keypair — unsafe to embed. Instead we derive a PDA:

seeds ["vault", vault_state] + program_id + bump  →  off-curve address
Because it is off the elliptic curve, there is mathematically no private key for it — so nobody can ever sign for it the normal way.
First principles

Why PDAs matter: only the program can sign

The program the PDA belongs to can sign on its behalf at runtime by handing the runtime the original seeds + bump — the "signer seeds".

This is the whole security model: SOL leaves the vault PDA only when our program presents the correct seeds — impossible for anyone else to forge. That is why withdraw is the only path that moves SOL out.
First principles

What Anchor gives us

  • Accounts structs — declare accounts + constraints; Anchor validates them first
  • Discriminator — 8-byte tag so the runtime knows the function
  • IDL — JSON interface used to generate client code
  • CPI helpers — CpiContext makes calling another program one line
So #[account(seeds=[...], bump)] means: "Anchor already proved this is the right PDA before calling your function."
