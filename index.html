The Anchor Vault, from first principles

A Solana program that lets a user lock SOL into a vault they control — and, in Task 2, registers them on another program during withdrawal. Start at 0; no Solana background assumed. Section 7+ maps directly to the repo you were given.

0Start here: Solana is one shared ledger

Imagine a single global spreadsheet everyone can read and a network keeps in sync. "Running a program" means proposing a change to that spreadsheet and getting it accepted.

Two ideas sit under everything:

  • Code (programs) and data (accounts) are separate things at separate addresses.
  • To change data you send a transaction that lists the data it will touch up front, so the network can validate it cheaply.
Hold that second point — it explains almost every line of code. You always declare your accounts before the program runs.

1A transaction is a bundle of instructions

A transaction = list of accounts + one or more instructions + signatures.

accounts[]
everything I'll read/write
instructions[]
program + which fn + args
signatures
proof I authorize it

An instruction is one call into one program: "run deposit with amount = 1 SOL, using these accounts." A transaction can chain several — that's how one action touches multiple programs (Task 2).

A signature proves the key owner agreed. An account marked "signer" had to sign; the runtime checks this before the program runs.

2Programs are stateless; accounts hold state

A program is deployed executable code at an address. It has no memory of its own between calls.

All lasting info lives in accounts: independent records addressed by their own keys. When a program runs, the accounts you passed in are its only inputs and the only things it can modify.

Mental shortcut: a program is a function; an account is a mutable argument you hand it.

3Anatomy of an account

Every account is just a record:

address
its public key
owner
which program may write its data
lamports
its SOL balance
data
arbitrary bytes (state lives here)
executable
true only for programs
signer / writable
flags set per-transaction

Two rules that matter for the Vault:

  • Only the account's owner program may change its data. Our vault program owns vault_state.
  • Only the owner (or System Program for SOL) may debit its lamports. That's why moving SOL out of the vault needs the vault's cooperation.

4Rent & why accounts cost SOL

Storing data costs a little SOL called rent. Creating an account pre-pays rent (recoverable by closing it).

In initialize, user is the payer. In close, close = user returns the rent when the account is deleted.

5PDAs: addresses that have no private key

We want a vault holding your SOL that only our program can empty. Normal accounts are owned by a keypair — whoever holds the key signs. We can't safely embed a secret key in code.

The trick: derive an address with no key

seeds
["vault", state.key]
+
program_id
our vault program
+
bump
→
PDA
off the curve

Because the result is forced off the elliptic curve, there is no private key for it.

The program the PDA belongs to can sign on its behalf at runtime by handing the runtime the original seeds + bump — the "signer seeds". The runtime recomputes the address, sees it matches, and accepts the signature.

That is the whole security model: SOL leaves the vault PDA only when our program presents the correct seeds — impossible to forge.

6What Anchor gives us

Raw Solana programs are verbose. Anchor generates the boilerplate:

  • Accounts structs — declare needed accounts + constraints (seeds, bump, mut, payer, init…); Anchor validates them first.
  • Discriminator — 8-byte tag so the runtime knows which function you called.
  • IDL — JSON interface used to generate client code (our TS tests).
  • CPI helpers — CpiContext + generated clients make calling another program one line.
So #[account(seeds=[b"vault", ...], bump)] means: "Anchor already proved this is the right PDA before calling your function."

pub fn withdraw(&mut self, amount: u64) -> Result<()> {

    Ok(())
}

11The big picture

State changes; code doesn't

The binary is fixed. Data inside the two PDAs changes: bumps on initialize, lamports up on deposit, down on withdraw, accounts gone on close.

One tx, three programs

With Task 2, a single withdraw touches Vault (logic), System (SOL), and Registration (record). Composability via CPI is the core idea.

One-liner: Programs = functions · Accounts = mutable args · PDAs = addresses only the program can authorize · CPI = one function calling another.

You now understand the repo file-by-file and what the current code does. When ready, we edit withdraw.rs (add the CPI + a github argument), deploy our own program to devnet, and run the TS test.

Cause → effect chains worth internalising

1. Stateless program → accounts passed in → vault_state stores bumps.
Because the program remembers nothing, every call must re-prove account identity. The vault_state PDA exists purely to persist the vault_bump/state_bump so the program can later re-derive & sign for the vault PDA.

2. PDA has no private key → only the program can sign (via seeds) → vault is safe.
The vault PDA is "off the curve", so no one can ever hold its key. SOL only leaves it when our program presents signer_seeds (seeds + bump). That makes withdraw the only path that can move SOL out — and the path we extended.

3. Signer status propagates through a CPI → registration accepts our user → account created by OUR program.
The user signed the outer transaction. Mid-execution, when we CPI into registration, that signer privilege carries over, so registration treats user as the signer that creates application_account. Crucially the CPI originates inside our deployed vault program — exactly what the grader checks.

4. One registration per wallet (enforced on-chain) → we deploy our own program → run once.
The registration program itself rejects a duplicate initialize. So the whole initialize→deposit→withdraw→close sequence must execute against a wallet that has not registered yet.
